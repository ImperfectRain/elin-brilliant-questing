# Actors

Current BQ actor integration centers on `Chara` and stable `Card.uid` bindings.

- `Chara.uid`, `Card.uid`, `Chara.source`, `Chara.isDead`, `Chara.currentZone`, `Chara.idFaith`, `Chara.elements`, `Chara.things`, `Chara.LV`, and `Chara._affinity` exist in the installed assembly (`VERIFIED-METADATA`).
- Player binding through `EClass.pc.uid` and debug reporting of the loaded PC succeeded in the current runtime log (`VERIFIED-RUNTIME`).
- BQ stores `EntityId <-> uid` mappings in `ElinBindings`; unresolved or stale bindings do not prove physical presence (`INFERRED`, backed by BQ code and D004).
- Actor classification is partially resolved. Installed `Card` exposes `IsUnique`, `IsImportant`, `c_uniqueData`, and `c_isImportant` (`VERIFIED-METADATA`). `IsUnique` is `rarity == Rarity.Artifact`; `IsImportant` is `sourceCard.HasTag(CTAG.important)`; `c_isImportant` is persisted int flag 109; `c_uniqueData` is persisted object slot 6 (`SOURCE-OBSERVED`). `Chara` also exposes `quest`, `memberType`, `faction`, `IsHomeMember`, `IsBranchMember`, `IsPC`, `IsPCParty`, and `IsGlobal` (`VERIFIED-METADATA`).
- Conservative relocation classification guidance: treat PC/party as never relocatable; treat `TraitUniqueChara`, `IsUnique`, `c_uniqueData != null`, adventurers, `IsImportant`, `c_isImportant`, active quest holders, and unknown trait/story rows as unsafe; treat BQ-generated actors as generated/safe only when BQ owns their creation; treat ordinary loaded non-global town citizens as not safe for Grade-B absence until movement probes prove a vanilla-safe path (`SOURCE-OBSERVED`, `INFERRED`, `UNRESOLVED` runtime samples).
- `Chara.idTimeTable`, `CurrentSpan`, `GetGoalFromTimeTable(int)`, `GetGoalWork()`, `GetGoalHobby()`, `Chara.global`, `GlobalData.goal`, `GlobalData.transition`, `TraitChara.UseGlobalGoal`, and `GlobalGoal.AdvanceHour()` exist (`VERIFIED-METADATA`). Which actors use them in ordinary play is unresolved (`UNRESOLVED`).

- Actor *classification* and settlement *residency* are different questions and only the first is answered today. `NarrativeActorClass` says how far the mod may reach into somebody; it does not say whether they belong to the place they are standing in, and it returns `OrdinaryCitizen` for anything the story flags do not claim. BQ-039a generation consequently admits any classified live actor in the zone, wildlife and passing hostiles included. No verified read closes this, and none was guessed at (ELIN-Q-0027).
- Narrative actor kind is now separate from mutation policy. `NarrativeActorKind` (`Unknown`, `Person`, `Animal`, `Creature`) and `SocialAgency` (`Unknown`, `None`, `Limited`, `Full`) are read into `LocalAffordanceProfile` so archetypes can constrain roles without deleting non-social actors from the local population. Petty theft requires `SocialAgency.Full` for thief/victim/witness roles; animals and unknown-agency actors remain visible to the profile and future archetypes.
- Live kind/agency classification uses the existing reflective source surface: `Chara.source`, source `job`/`idJob`/`hobby`/`work`, source `category`/`tag`/`tags`/`type`, race metadata reachable from source `race`, `Chara.idRace`/`idActor`/`idChara`, and trait type names. These members are `VERIFIED-METADATA`/`SOURCE-OBSERVED` where already listed above; the mapping from source text to `Animal`/`Creature`/`Person` is conservative and `INFERRED`. Unreadable or unfamiliar shapes remain `Unknown`, and `Unknown` fails closed for roles that explicitly require social agency.

- Character identity is read as its own observation at the seam (`GetCharacterIdentity`, BQ-144) with six separately typed facets: character archetype (`SourceChara` row id and `aka`), race (`Chara.idRace` and the race row), work (source `job`/`idJob`), hobby (source `hobbies`), service role (shop/trade trait subclasses, with the trait type name carried verbatim) and institutional role (`TraitGuard`, `TraitGuildPersonnel`, `TraitGuildDoorman`, plus `Chara.faction`). The trait types are `VERIFIED-METADATA`; the source columns are `SOURCE-DATA`; which of them are actually populated on ordinary townspeople is `UNRESOLVED` until a live population is logged. Each facet is read independently, so a member this build no longer exposes costs its own facet only, and an unread facet is `Unknown` rather than `""`, `"local"`, `false` or a default job.
- Identity is observation, not interpretation: nothing derives personality, plausible knowledge, interests or eligibility from it yet (BQ-145), and it is not an input to `NarrativeActorClass` or the mutation policy. It is a live read and is never persisted; the pre-BQ-144 placeholder `NarrativeNpc.Occupation = "local"` is no longer written and a saved one is dropped on load. The guard/guild trait read that used to write `NarrativeNpc.Roles` directly is now the institutional facet, interpreted once in `ElinAuthorityRoles`.
- Per-character institutional rank is still unread: `FactionRelation.rank` is the player's own standing (ELIN-Q-0025), so an NPC's rank is reported as unknown rather than zero.

- The player's own household is read as two separate things (BQ-123). Residency comes from the settlement branch and is unchanged; the party is read through `EClass.pc.party` and its member list (`members`/`Members`/`charas`), resolved by name like everything else below `EClass.pc` that has never been read off a running game. `Chara.IsPCParty` is `VERIFIED-METADATA` and confirms the concept exists on `Chara`; the member that *lists* the party is `UNRESOLVED` (ELIN-Q-0029), so a build that names none of the candidates reports `ReadPlayerCompanions` unsupported and the household is the Home roll alone - never an empty party, which would be the mod claiming the player travels alone.
- Household membership is a live read and is never persisted, on the same terms as the Home snapshot and the identity observation. It is `HouseholdBond` (`Resident`/`Companion`) and nothing more: what a companion *is* stays `GetCharacterIdentity`'s six facets, whether it can carry a social role stays `SocialAgency`, and how far the mod may reach into it stays `NarrativeActorClass` - a party member is already `StoryCritical` there and BQ-123 does not touch that.

Current consumers: `ElinVanillaState`, `ElinBindings`, `ElinActorClasses`, `ElinCharacterIdentity`, `ElinAuthorityRoles`, `ElinPlayerCompanions`, `ElinActionObserver`, `DramaChoiceProjector`, `ElinSituationStager`.
